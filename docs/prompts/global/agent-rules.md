# Global Agent Rules

Use these rules at the start of work in any STREM repository.

## Product authority

STREM is the AI race team for self-coached trail runners preparing for demanding events. Trail running is the only active sport until paid value and retention are proven.

Read:

1. `product/trail-running-pivot.md`
2. `product/trail-running-delivery-plan.md`
3. `product/implementation-status.md`

If another document conflicts, these three win.

## Anti-drift test

Before building or documenting anything, ask:

1. Which real Race Mission decision, rehearsal, risk, or operation does this improve?
2. Does it work for an athlete training alone?
3. Is it meaningfully different from a tracker, generic plan, event listing, or chat wrapper?
4. Can the recommendation name its evidence, provenance, assumptions, confidence, and missing data?
5. Is manual evidence still a first-class path?
6. Does the change protect consent, safety, athlete control, and honest uncertainty?
7. Does it support the paid trail validation gate now?

If the answers are weak, narrow, park, or remove the work.

## Active product loop

1. Commit to a real event.
2. Understand event demands and athlete constraints.
3. Create an inspectable preparation map.
4. Update evidence through imports and fast manual check-ins.
5. Explain progress, risks, and proposed adaptations.
6. Rehearse terrain, fueling, equipment, and conditions.
7. Execute race-week and race-day operations.
8. Debrief and preserve learning for the next event.

## Explicit exclusions

Do not reintroduce these without a new founder decision backed by validation:

- generic activity, calorie, wellness, or analytics dashboards;
- XP, ranks, medals, streak rewards, seasons, proof walls, or collectible progression;
- mandatory community, Tribe, Crew personas, follower graphs, leaderboards, or public likes;
- generic AI chat detached from a Race Mission;
- fabricated athlete data, readiness, recovery, source history, or race facts;
- biomarker, supplement, marketplace, cinematic recap, or broad multi-sport scope;
- a generic race calendar with no structured organizer data or commercial reason.

## AI behavior

- Use only consented context.
- Separate recorded facts, calculations, athlete statements, assumptions, and unknowns.
- Cite the evidence that materially affected a recommendation.
- Propose consequential plan changes; do not apply them invisibly.
- Keep changes inspectable, editable, rejectable, and reversible where possible.
- Escalate injury, illness, nutrition, mental-health, and medical concerns instead of diagnosing or prescribing.
- When a live capability fails, show an honest unavailable state; never substitute mock personal data.

## Engineering rules

- Read the workspace and repository `AGENTS.md` files.
- Work from a scoped issue, an active plan, or explicit founder instruction.
- Preserve unrelated user changes.
- Keep repository and service boundaries intact.
- Do not change public contracts, auth, privacy, health behavior, migrations, or deployment without the required review gate.
- Prefer the smallest vertical slice that strengthens the Race Mission loop.
- Remove obsolete code rather than retaining a second product direction.
- Add tests in proportion to risk and update active documentation when behavior changes.

## Finish report

Report:

- the Race Mission outcome improved;
- what changed and what was removed;
- how it was verified;
- which data is real, unavailable, or prototype-only;
- remaining review gates or risks.
